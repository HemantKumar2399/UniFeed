# Epic 2 Retrospective - Platform (UniFeed)

## 1) Epic Review

### Outcome Summary
- **Epic completion status:** complete in sprint tracker.
- **Stories completed in sprint tracker:** 2-1, 2-2, 2-3, 2-4, 2-5, 2-6.
- **Core scope delivered:** Feed Database Seeding Mock APIs, Static Event Geometry, Card Interactions, Ephemeral Story Bar Component, Story Deep-Linking Logic, High-Fidelity Skeleton Loaders.

### What Went Well
- **Performance:** Strict adherence to sub-500ms interaction constraints. Achieved through a lean approach relying heavily on pure CSS (grid transitions, scroll-snap, keyframes) and native browser APIs (URL hash states) over heavy React libraries.
- **UX & Accessibility:** Strong enforcement of UX design tokens. Achieved Cumulative Layout Shift metrics (CLS) at 0, explicit ADA color contrast gradients (`bg-gradient-to-t from-black/90`), motion-safe logic (`motion-safe:` utility class), and proper semantic DOM mapping (ARIA tags).

### What Was Painful
- **State Management & Communication:** Developers struggled with isolating state effectively (e.g., tap-to-expand state localized to individual cards) and managing deep-linking state across sibling components (`StoryBar` to `EventCard`). Using the URL hash to trigger cross-component interaction helped but caused complications.
- **Execution Gaps in System Integration:** Standalone components were mapped out correctly, but integrating them into the broader system highlighted gaps. Examples: forgetting to import/render the `StoryBar` within the feed layout, executing destructive database seed scripts unsafe for remote environments, and introducing UI glitches with URL hash navigation and `scrollIntoView()`.
- **Skeleton Layout Shifts:** Achieving 0 CLS was difficult due to discrepancies between the root wrapper components of the `FeedSkeleton` and the live layout tree (`HomePage`), making the skeleton setup redundant until the reviewer identified the layout issue.

### Pattern Insights
- **Review Layer Saves:** For a second Epic in a row, the review phase proved its value by consistently catching missed integrations (e.g. absent `StoryBar`), bad semantic HTML (`<div onClick>` vs `<button>`), and unsafe DB commands. Better pre-review checklists are required.
- **Aggressive Preference for "Lean" Solutions:** This is becoming our default pattern—using raw CSS/browser features over libraries. While great for performance, it requires meticulous testing of browser API side-effects (like native scroll race conditions).

- **Action Item 3 (Move review hardening earlier in story lifecycle):** The gap in implementation logic (missing StoryBar) still only surfaced during the formal AI Code Review layer. Mid-implementation review points are still not occurring natively. - ⏳ In Progress

## 3) Keep / Improve / Stop

### Keep
- Relying on pure CSS, Tailwind utilities, and native Browser APIs instead of pulling in bloated 3rd-party libraries.
- Strict enforcement of ADA accessibility rules, ARIA tags, and Zero CLS targets.

### Improve
- System and component integration checking. Developers need to make sure the app maps to the DOM as a whole, not just isolated files in a directory.

### Stop
- Using `div` with `onClick`—semantic interactive elements (`button`, `a`) must be utilized moving forward.
